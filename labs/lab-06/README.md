# Лабораторная 6. Микросервисы: маркетплейс

Микросервисы, примерно 4 нед. Открывается после станции «gRPC, WebSocket и real-time».

Главная лабораторная по микросервисам: синхронное и асинхронное взаимодействие, распределённая транзакция через сагу, отсутствие потерь и дублей.

## Стек

- Go
- gRPC и buf
- Kafka
- PostgreSQL (база на сервис)
- Redis
- Docker Compose

## Требования

- Сервисы: gateway (REST наружу, gRPC внутрь), catalog (товары и остатки), order, payment (эмулятор банка), notification.
- Оформление заказа — сага: создать заказ, зарезервировать товар, списать оплату, подтвердить. При отказе оплаты резерв снимается.
- События публикуются через transactional outbox, обработчики идемпотентны (inbox-таблица по event_id).
- Idempotency-Key на создание заказа в gateway.
- У каждого сервиса своя база, общих таблиц нет.
- Дедлайны и ретраи на gRPC-вызовах, circuit breaker к payment.
- Контракты в proto и схемах событий лежат в отдельной папке и версионируются.

## Этапы

1. Контракты: proto-файлы и схемы событий, диаграмма последовательности саги.
2. Catalog и order, синхронный поток через gateway.
3. Kafka, outbox-релей, payment и сага с компенсациями.
4. Notification, DLQ, e2e-тест всего сценария.
5. Сценарии отказов.

## Структура проекта

```
marketplace/
  api/proto/              # контракты gRPC
  api/events/             # схемы событий
  services/gateway/
  services/catalog/
  services/order/
  services/payment/
  services/notification/
  pkg/outbox/             # общая библиотека релея
  deploy/docker-compose.yml
  tests/e2e/
```

## Критерии приёмки

- [ ] Остановка payment посреди оформления: после восстановления все заказы в конечном состоянии, ни одного зависшего резерва.
- [ ] Повтор запроса с тем же Idempotency-Key не создаёт второй заказ.
- [ ] Повторная доставка события из Kafka не меняет результат.
- [ ] `make up` поднимает всю систему, e2e-тест проходит.
